# 实现约束

在修改代码、调整架构、改动主题/i18n 或声明验证结果前读取本文件。

## 开发规则

修改前：

1. 理解用户需求和边界。
2. 检查现有仓库结构和相关文件。
3. 查找可复用组件、hooks、stores、utils、types、data 和样式。
4. 判断任务是否影响路由、主题、国际化、SEO、数据或共享类型。
5. 确定验证方式。

修改中：

- 保持修改聚焦。
- 遵守现有约定。
- 优先拆成小而清晰的组件。
- 结构化静态数据放在 `src/data/`。
- 共享类型放在 `src/types/`。
- 可复用组合式逻辑放在 `src/hooks/`。
- 纯工具函数放在 `src/utils/`。
- 主题 token 和主题适配放在 `src/themes/`。
- 翻译文案放在 `src/locales/`。

修改后：

- 运行可用的验证脚本。
- 如果脚本缺失，说明缺失原因并给出手动检查步骤。
- 只汇报实际验证过的内容。

## Vue 与 TypeScript

使用：

- Composition API。
- `<script setup lang="ts">`。
- 类型化 props。
- 类型化 emits。
- 必要时为路由参数提供类型。
- 明确的数据模型。

避免：

- 大范围使用 `any`。
- 用类型断言掩盖真实数据问题。
- 页面组件承担过多职责。
- 在组件内复制共享业务数据。

## 组件

按以下类别组织：

- `common/`：跨页面公共组件。
- `layout/`：应用外壳、导航、页脚和容器。
- `business/`：作品集业务模块。
- `ui/`：Naive UI 封装和底层 UI 原语。

组件规则：

- 保持单一清晰职责。
- 基础控件优先使用 Naive UI，不重复造轮子。
- 视觉变体必须可主题化。
- 不为一次性需求创建公共组件。
- 数据驱动组件要处理空状态、加载状态和错误状态。

## 主题保护

不要在组件中硬编码主题敏感颜色。避免直接写 `#000`、`#fff` 或一次性品牌色，除非这些值已经先定义为 token。

使用：

- CSS variables。
- Tailwind 语义化颜色。
- Naive UI theme config。
- 主题 store 或 provider。

主题改动必须保留：

- 深色模式。
- 浅色模式。
- 跟随系统。
- 用户偏好持久化。
- Naive UI 与 Tailwind 同步。

## 国际化保护

不要在 Vue 模板或页面数据中硬编码完整用户可见文案。

使用：

- `t('key')` 管理 UI 文案。
- 必要时使用支持多语言字段的结构化内容。
- 保持 key 命名一致。

新增文案时：

- 添加 `zh-CN` key。
- 如果存在 `en-US` 和 `ja-JP` 文件，保持同样 key 结构。
- 页面变化时同步更新 SEO 和路由标题。

## SEO

每个路由应具备：

- 国际化标题。
- 国际化描述。
- 适合 Open Graph 的元信息。
- 语义化 HTML。

新增页面时同步更新：

- 路由 meta。
- 页面标题国际化。
- 分享摘要。
- sitemap 或静态部署兼容逻辑。

## 性能

优先：

- 路由级懒加载。
- 静态数据优先，除非确实需要动态请求。
- 图片压缩并设置明确尺寸。
- CSS transition 优先于重型动画库。
- 控制依赖体积。

避免：

- 为小交互引入大型依赖。
- 无边界背景动画。
- 对静态作品集数据重复请求。
- 因缺少尺寸导致布局跳动。

## 验证

优先使用项目已有脚本：

```text
npm run lint
npm run typecheck
npm run test
npm run build
```

如果脚本不存在，使用最接近的检查方式，并说明手动验证步骤。

UI 变更至少检查：

- 桌面布局。
- 移动端布局。
- 深色模式。
- 浅色模式。
- 主要路由导航。
- 文本没有明显溢出或重叠。

## Git 与文件安全

- 大幅修改前查看 `git status`。
- 除非用户要求，不执行删除、reset、revert、commit、push 或重写历史。
- 不修改无关脏文件。
- 不隐藏失败，不声称未运行的测试已通过。
- 不提交密钥、token、私钥或真实凭据。
- 提交信息使用简体中文，格式为 `type: 中文摘要`，正文必须写清改了什么以及改了哪些文件。
